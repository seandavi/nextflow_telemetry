## Summary

The Microbiome Repo is a bitemporal, evidence-linked metadata catalog over INSDC (ENA/SRA/DDBJ) human shotgun metagenomes, not a profile or output store. It has a registry tier (64,369 studies, 637,397 BioSamples), a human-gut catalog tier (2,798 current studies, 573,001 current curated samples, 718,658 runs), and an infant extension (389 studies, curated in more depth). Every curated value carries a route (R1-R4), an ordinal confidence, and a verbatim evidence quote of 12 words or fewer. LLMs (Claude Haiku/Sonnet/Opus) do much of the study classification and paper/abstract reading, and the site says model-based calls are not human-reviewed. A parallel table family reports taxonomic profiles (Sandpiper 2.0.0, GTDB R232) for about 59% of catalog samples. It overlaps our work on the *which samples exist and what are they* side, not on the *what does our pipeline say about them* side. The most useful things we can take are the accession lists (find studies we haven't registered) and a second-opinion metadata source with provenance. The license (CC-BY-4.0) is easy to meet.

## What it is

- **Tiers** ([downloads](https://olmlab.github.io/microbiome_repo/downloads/index.html), [README](https://olmlab.github.io/microbiome_repo/data/package/README.md), [methods](https://olmlab.github.io/microbiome_repo/about/methods.html)):
  - *Registry* (`registry_*`): every INSDC BioProject with METAGENOMIC or WGS-type runs, enumerated from the ENA portal API in dated slices. 64,369 studies, 63,952 (99%) classified, 417 pending. Classified for host, assay, UBERON-anchored body site (17 terms), and life stage.
  - *Catalog* (`gut_*`): human host + shotgun assay + gut/stool among body sites. Every harvested BioSample of such a study becomes a catalog sample.
  - *Infant extension*: 389 infant-gut studies curated earlier and deeper (`curated_source = infant_catalog`; `infant_scope = true` reproduces the old infant catalog).
- **Headline vs current counts.** The downloads page and README headline say 2,946 studies / 602,163 samples; the release notes say 2,798 studies / 573,001 samples. Verified locally: `gut_studies.parquet` has 2,946 rows, of which 148 (21 infant + 127 `gut_all_v1`) have a non-null `release_retired`. The remaining 2,798 current rows have `sum(n_samples_curated)` = 573,001, which matches the release notes. So the headline counts include retired rows. Always filter `release_retired IS NULL` before counting.
- **Prefix mix of the 2,946 `gut_studies` rows** (verified locally): PRJNA 2,107, PRJEB 732, PRJDB 101, SRP 6.
- **Release model** ([downloads](https://olmlab.github.io/microbiome_repo/downloads/index.html), [VERSION.json](https://olmlab.github.io/microbiome_repo/data/package/VERSION.json)): 30 releases between 2026-09-25 (1.0.0) and 2026-10-12 (R2026.25), so about 2.5 a week, each with a `data-v<pkg>` tag and a `site-v<pkg>` tag. Release IDs (R2026.n) map to package versions (e.g. R2026.25 = 1.20.0). Fact tables carry `release_added`, `release_retired` (null = current) and `package_added`, and `releases.csv` is the registry. "Releases are immutable" and `manifest.json` / `VERSION.json` list SHA-256 and `size_bytes` per file. Concept DOI [10.5281/zenodo.23087712](https://doi.org/10.5281/zenodo.23087712) covers all versions. The generator is a separate repo, `OlmLab/microbiome_repo-pipeline` (commit `654f5f4` per VERSION.json); I did not read that repo.
- **Distribution**: the 171.6 MB `data_package_v1.20.0.zip` and per-file Parquet from GitHub Pages and the GitHub release. Large profile tables are release assets only (about 2M-row `registry_runs_v1.20.0.parquet` ~80 MB; Sandpiper genus ~185 MB and species ~200 MB long tables; `sandpiper_profiles.parquet` ~100 MB; an all-in-one SQLite).

## Methods

Sources: [methods page](https://olmlab.github.io/microbiome_repo/about/methods.html), [README](https://olmlab.github.io/microbiome_repo/data/package/README.md).

- **Study classification.** 52,142 studies are classified by deterministic rules on archive fields. About 6,800 more use two independent model replicates (5,164 agree; 1,663 go to a stronger model for adjudication), and the remainder use earlier-triage priors (4,808), owner decisions (96), and curator audits (79). Every call keeps its evidence rows. "Model-based calls are not human-reviewed."
- **Sample-value routes** (precedence R1 > R2 > R3 > R4 per sample and field):
  - R1: BioSample attributes via a field map and deterministic parsers. A model triages ambiguous *keys*, never values.
  - R2: open-access supplementary tables, used only when sample IDs join exactly (>=50% of rows or >=20 hits). No model.
  - R3: paper full text. Two Sonnet-class replicates must agree and the quote must be a verbatim substring. Case-control group statements are never applied to samples.
  - R4: abstract/title/ENA description, one utility-model request per study, cohort-wide statements only, confidence <=0.5.
- **Confidence** is an ordinal engine tier, "not a calibrated probability." Empirical precision per tier and field is in `tier_field_precision.csv` (49 rows), which I did not read. The README says to use R1/R2 values at any confidence and R3/R4 only at >=0.5.
- **Models by role** ([README](https://olmlab.github.io/microbiome_repo/data/package/README.md)): Haiku for screening/normalisation, Sonnet for rubric judgement and prose extraction, Opus for adjudication. The exact model per row is in `determined_by`. Deterministic code handles units, subject propagation and date arithmetic.
- **QC.** Conflicting attributes are not committed and are logged. `gut_pass_coverage.csv` records whether each annotation pass ran, and the release fails if a pass never ran without a recorded exception. Deep-pass values agree with existing values for sex, country and age in >=98% of compared samples. Human review is limited (`human_review_queue.csv`, 52 studies).
- **Sandpiper profiles** ([report](https://olmlab.github.io/microbiome_repo/data/package/GUT_SANDPIPER_REPORT.md)): Sandpiper 2.0.0 (Zenodo 20419175) profiles with GTDB R232 taxonomy cover 372,911 of 721,678 runs (51.7%) and 339,626 of 579,252 samples (58.6%) in 2,084 studies. Samples are flagged, never dropped (12.35% carry at least one flag, e.g. low complexity 3.33%, strict non-metagenome 4.72%, low depth 0.6%). The report does not say what Sandpiper is. Column names (`root_coverage`, `spf`) are consistent with a SingleM-style marker-gene profiler, but no fetched page says so. UNVERIFIED. The 490 MB run-level table is not shipped.

## Findings: coverage and benchmark

- **Coverage of curated fields over gut samples** ([release notes](https://github.com/OlmLab/microbiome_repo-data/releases/tag/data-v1.20.0)): age 28%, sex 33%, country 91%, health condition 49%, antibiotic exposure 20%. The methods page gives slightly different figures (age ~29%, health ~50%, sex 34%), likely from an earlier snapshot. Age is recoverable for about 37% of infant-scope samples, but only all-or-nothing per study.
- **Benchmark against curatedMetagenomicData** ([downloads, tail](https://olmlab.github.io/microbiome_repo/downloads/index.html), `extraction_gold_eval_hires.csv`, 6 rows): this is the cMD hi-res gold set, restricted to infant-extension fields. Precision/recall: age_days 0.991 / 0.951 (n=3,346), born_method 0.995 / 0.932, premature 1.000 / 0.961, antibiotics_current_use 0.867 / 0.820, feeding_practice 0.891 / 0.577, gestational_age 1.000 / 0.264. The page reports identical values in every release from 1.2.2 to 1.13.0, so it does not show whether the benchmark is re-run. The README also cites precision on the full cMD set (age 0.976, delivery 0.995, preterm 1.00).
- **Not validated**: exposure fields (probiotic, HMO, NEC, birth weight, maternal antibiotics) have no external truth set and were checked only by blind model re-judgement ([README](https://olmlab.github.io/microbiome_repo/data/package/README.md)).
- **What a published benchmark number does not cover**: the benchmark is for infant fields. The adult/gut-all tier (`gut_all_v1`, 2,430 current studies of the 2,798) has no stated gold comparison in what I read. UNVERIFIED whether one exists in the CHANGELOG.

## How we can leverage this

1. **Find studies we have not processed (highest value).** `gut_studies.study_accession` (current rows only) and `registry_studies.study_accession` are BioProject lists that `docs/adding-studies.md` can take as input: the add-study issue form requires a study/BioProject accession (PRJ.../SRP/ERP/DRP; a run or sample accession is rejected) and posts a dry-run preview of sample counts and library composition. Plan: anti-join their current gut studies against our collections, rank by `n_runs`, `cov_age_at_collection_days`, `cov_health_condition`, and `gbp_per_sample_median`, then feed the top ones through the existing issue/approval flow. `gut_runs.library_strategy/source/layout/instrument_platform` pre-answers the dry-run's "shotgun WGS Illumina" sanity check, and `n_runs`/`gbp_per_run_mean` give a cost estimate against `docs/research/resource-tuning-2.3.0.md`. Run-level join key is `gut_runs.run_accession` / `sample_accession` (BioSample) to our `samples` rows. I have not verified what our `samples` accession columns are called. Check `src/nextflow_telemetry/db.py`.
2. **Cross-check our sample metadata against theirs.** For samples we share, compare our `samples`/curated annotations (see `docs/sample-metadata-design.md`) against `gut_sample_metadata_wide` on `biosample_accession`. Their wide table gives age in days, sex, country, health condition and `antibiotic_exposure`, each with route, confidence, and quote. Use R1/R2 values at any confidence and R3/R4 only at >=0.5, per their README. Disagreements are a cheap QC signal in either direction. Their `gut_metadata_contradictions` also flags samples whose own metadata is incoherent, which is a candidate exclusion list.
3. **Fill gaps in our metadata, with provenance.** Fields we may lack (body site code, `age_category`, `health_condition` vocabulary, `collection_date`, `lifestyle`, `bmi`) could be imported as annotations with `source = microbiome_repo`, `release = R2026.25`, and their `__route`/`__confidence` kept. Their `release_added`/`release_retired` columns map naturally onto a version-stamped import and would let us re-sync per release.
4. **Study relatedness and dedup.** `gut_studies.study_group_id`/`study_group_basis`/`study_group_members` and `gut_relatedness`/`gut_relations` group studies and samples that share cohorts, donors, families or twins. This is relevant to the many-to-many sample-to-study model in `docs/study-sample-version-identity.md`: the same BioSample can sit in two BioProjects (README says 62 do), and cohort-level leakage matters for downstream ML. Use it as an advisory, not authoritative, grouping.
5. **GTDB comparison.** Their profiles are GTDB R232 (genus and species long tables as release assets). Our `gtdb_profile` is MetaPhlAn relabelled to GTDB through the SGB-to-GTDB map (`docs/output-catalog-etl-design.md`, Taxonomy harmonization), so a species or genus-level concordance check on shared samples is feasible. Expect differences: a different profiler, a different GTDB release, and different handling of unassigned reads. Compare at genus level with a rank-aware metric and note that GTDB suffixes such as `Enterococcus_B` are not NCBI names ([notebook caveat](https://olmlab.github.io/microbiome_repo/data/package/getting_started.ipynb)). Only the release-asset tables carry abundances; I did not check their schemas. UNVERIFIED.
6. **Their QC flags as a screen for our inputs.** `qc_non_metagenome_strict`, `qc_low_depth`, `qc_low_complexity`, `qc_synthetic` in `gut_sandpiper_sample_summary` could pre-flag samples likely to waste SLURM hours or to produce empty profiles (relevant to the cost model in `resource-tuning-2.3.0.md`). Only 59% of samples are profiled, so absence of a flag is not evidence.
7. **License and citation.** Curated tables are CC-BY-4.0, archive metadata stays under INSDC terms ([downloads](https://olmlab.github.io/microbiome_repo/downloads/index.html)). If we ingest or redistribute any of it (including via `cmgd-public` or the lake), credit "Microbiome Repo, release R2026.25 (data package 1.20.0), OlmLab, 2026-10-12" plus the concept DOI, and state that values are derived. The README says its own citation is "a placeholder in the source, so confirm the final citation before publishing", so check with the authors before publication. The site repo has no stated license (`OlmLab/microbiome_repo`).

## How we are differentiated

Grounded in `CLAUDE.md`, `docs/roadmap.md`, `docs/output-catalog-etl-design.md`, `docs/storage-layout.md`, `docs/study-sample-version-identity.md`.

- **We run the pipeline and own the profiles; they curate metadata.** We process raw reads through `cmgd_mpa4.2` (MetaPhlAn 4.2.6, vJan26 index, with marker abundance), alongside kraken2/bracken, resistome and optional HUMAnN/StrainPhlAn outputs (`output-catalog-etl-design.md`). Their taxonomic profiles come from a third-party service (Sandpiper) on a subset of samples, and they do not publish marker-level data in anything I read. We are ahead on per-sample, strain-capable, marker-level outputs; they are ahead on metadata breadth.
- **Orchestration.** `CLAUDE.md` describes pull-mode dispatch: nf-client daemons on Alpine and Anvil claim jobs over outbound HTTPS from the Worker (`cf/`) with job states `pending -> claimed -> submitted -> running -> completed`, retry budget, and a dead-letter queue. The Microbiome Repo is a data release process with no execution layer that I could see.
- **Versioned workflow registry and runs.** We register workflow revisions, run per-sample jobs, and treat "complete" as version-scoped (`study-sample-version-identity.md`, Decision 3). They version the *catalog* (bitemporal columns, immutable releases), which is complementary: ours versions computation, theirs versions annotation.
- **Per-sample provenance.** Each sample's `manifest.json` records read accounting, DB versions and parameters (`output-catalog-etl-design.md`), and telemetry events record each task. Their provenance is per *value* (route, confidence, 12-word quote), which is finer-grained on the metadata side than anything we have. We have no equivalent for curated metadata and should not claim parity.
- **Output catalog.** Our plan is DuckLake on R2 (`cdsci-lake`, `docs/storage-layout.md`) with per-method tables split by grain and datatype, and markers at roughly 89% of rows by row count. Their equivalent is flat Parquet in a zip, with the abundance tables shipped as release assets.
- **Where they are ahead.**
  - Study discovery and breadth: 64k registry studies and 637k harvested BioSamples, with a classified human/assay/body-site/life-stage label for each study.
  - Metadata curation at scale with evidence quotes, a conflict-withholding rule, and a formal confidence/route vocabulary.
  - Release engineering: 30 immutable, hash-checked releases in 17 days, a DOI, and a notebook.
  - Cohort/relatedness annotations and study-group clustering.
  - Published benchmark against cMD (even if limited to infant fields).
- **Where we are ahead.** Real reprocessing (a uniform, versioned pipeline on raw reads rather than a patchwork of archive metadata), marker-level and strain-capable outputs, a live orchestration and monitoring layer, and a path to a queryable output lake. Our sample metadata is the weak point (`roadmap.md`, Epic A and the sample-metadata work), which makes their tables a useful input rather than a competitor there.

## Caveats

- **LLM-assisted, partly unreviewed.** The site tells users to "treat values as evidence-linked claims" ([downloads tail](https://olmlab.github.io/microbiome_repo/downloads/index.html)). R3/R4 are group-level statements applied to samples and are the riskiest values.
- **Internal inconsistencies** in the docs: headline vs current counts (above), dictionary vs manifest row counts, and R1 confidence range (0.85-0.9 in the dictionary vs 0.7-0.9 on the methods page). The README itself tells users to "verify against `VERSION.json` and `releases.csv`" before reporting totals.
- **Moving target.** About 2.5 releases per week so far, with retired rows (148 of 2,946 studies in 1.20.0). Pin the release ID and filter `release_retired IS NULL` (verified locally on `gut_studies`).
- **Coverage is thin for the fields we care about** (age 28%, antibiotics 20%; many case-control cohorts remain unknown at sample level).
- **Scope**: human gut, shotgun. Registry covers other body sites, but only with study- and BioSample-level labels, not curated sample metadata.
- **Notebook issues** ([getting_started.ipynb](https://olmlab.github.io/microbiome_repo/data/package/getting_started.ipynb)): it is written against the older v1.2.1 infant tables (154,206 rows x 147 columns), does not demonstrate a `gut_runs` join, and has at least one cell assuming one run per sample.
